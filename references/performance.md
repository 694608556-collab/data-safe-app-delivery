# 性能定位与逐次验收

## 测量约定

先确定用户感觉慢的是哪一段：点击后无反馈、完整草稿/结果等待、联网批次结束、保存完成，还是首次启动。分别记录响应时间和完整结果时间；进度条出现不等于处理完成。

每组结果至少关联：源码/构建、设备与系统、应用是否调试、输入身份和规模、网络/缓存状态、计时起止点。目标值来自本次约定；不要继承案例中的数值。

要求首次与后续都达标时，各格式/操作独立冷首测，逐次列出完整耗时与结果。首轮失败不能被预热后的均值掩盖。联网缓存命中、离线重放和真实在线获取分别报告。

## 先拆耗时，再选择改动

沿真实路径测量，不固定要求每项都建探针：

```text
用户动作 → 选择/读取 → 网络/排队 → 解码/解析 → 规范化/校验
→ 编码/摘要 → 跨层传输 → 原生校验 → 暂存/事务 → 预览/搜索呈现
```

记录最长段与关键路径。可以重叠的任务只在资源和正确性允许时重叠；计算耗时不能简单把重叠阶段相加。

| 观察 | 候选方向 | 必须验证 |
| --- | --- | --- |
| UI长时间无反馈 | 将重任务移出UI线程，先提交轻量状态 | 真实结果仍完整；取消/关闭生命周期正确 |
| 网络已完成但批次仍慢 | 解析、传输、保存和队列收尾 | 正常联网全流程，不只测下载 |
| 旧正文反复读取或编码 | 增量写入、引用旧内容、一次读取索引尾值 | 旧正文、顺序、关联、重启和CAS不变 |
| JS/原生桥接复制占比高 | 不可变候选、减少往返、无损压缩 | 字节/业务差分、资源失败完整回退 |
| 并发越多越慢或内存飙升 | 限制实际网络、展开正文与上传租约 | 关闭/失败后所有任务结算，无泄漏和部分提交 |
| 单独快，整套CI冷首测慢 | 隔离冷格式或主机资源争用 | 不预热过关，不改原时限，保留失败证据 |

## 并发不是一个数字

区分实际网络请求、排队任务、展开正文数、编码任务、上传租约、数据库事务。按设备资源和服务行为分配预算。

增大在途数前先确认瓶颈可并行、峰值可承受、上游允许以及失败能被完整收敛。批次的最终原子保存不能因流水线提速变成多个半成品提交。

真实网络有波动，目标应与当前验收约定一致；不能为了漂亮数字跳过慢链接、减少正文、把失败算成功或偷偷改变重试/超时策略。明确报告成功、失败、手动正文和最终保存状态。

## 快速路径的准入与回退

给新路径写明可证明等价的条件；不满足条件时走原完整路径，不把合法输入当错误。不要把CPU架构、语言字符串语义和编码规则想当然。

对比同一输入、同一优化构建方式下的新旧路径；检查完整输出以及拒绝/接受结果。相关原生代码须按目标32/64位或实际支持架构运行验证。

## 避免把开发过程本身拖慢

- 先用一个有效回归定位，不在每个小改之后全套重建所有平台。
- 在既定阶段完成针对性检查，再跑约定全量；源变化影响已有证据时重跑受影响项。
- 独立任务可并行，同机重型测试先判断资源争用。代理分工遵循当前环境权限，不强制固定代理数量。
- 保留失败，比较新旧结果，明确淘汰候选；不要对同一个未知失败无限重试。
- 对用户报告关键路径上的发现和下一步，结束时给出完整结果；不把“继续优化”无限延长为没有交付点的任务。
